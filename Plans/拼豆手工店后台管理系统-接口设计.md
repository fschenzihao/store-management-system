# 拼豆手工店后台管理系统接口设计

## 1. 文档定位

本文档是阶段四确定的前后端通信契约，覆盖手工品类、客户、客户账户、充值记录和消费记录。阶段五的正式数据接口、Mock 数据与前端页面必须以此文档为字段基线；如需变更，应先更新本文档，再同步修改实现。

数据访问层类型位于 `apps/backend-mock/db/dal/`，资金事务入口位于 `apps/backend-mock/db/transactions.ts`。

## 2. 通用约定

### 2.1 地址与认证

- 下表路径均为前端 `requestClient` 使用的相对路径；服务端完整路径带 `/api` 前缀，例如 `/customers` 对应 `/api/customers`。业务接口直接位于 `/api` 根路径下，不使用业务域前缀。
- 写接口请求体使用 `application/json`。
- 所有接口沿用现有后台认证机制，请求头携带 `Authorization: Bearer <accessToken>`。
- 路径参数和 ID 字段均为大于 0 的安全整数。

### 2.2 响应包装

成功响应：

```ts
interface ApiSuccess<T> {
  code: 0;
  data: T;
  error: null;
  message: 'ok';
}
```

失败响应：

```ts
interface ApiFailure {
  code: -1;
  data: null;
  error: {
    code: string;
    message: string;
  };
  message: string;
}
```

- 前端请求拦截器以顶层 `code === 0` 判断成功，并直接返回 `data`。
- 业务错误码从 `error.code` 读取；`error.message` 与顶层 `message` 均为可直接展示的中文提示。
- 与现有 Mock 业务接口一致，参数、数据冲突和资金校验等预期业务错误使用 HTTP 200 配合顶层 `code: -1`；认证失败仍使用 HTTP 401/403，未知服务端异常使用 HTTP 500。
- 未知异常统一返回 `INTERNAL_ERROR`，不得向前端暴露 SQL、数据库路径或错误堆栈。

失败示例：

```json
{
  "code": -1,
  "data": null,
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "余额不足：当前 1000 分，需要 1001 分"
  },
  "message": "余额不足：当前 1000 分，需要 1001 分"
}
```

### 2.3 字段格式

| 字段类型 | 约定 |
| --- | --- |
| 金额 | 使用字段名带 `Cents` 的整数分，不接收或返回浮点元金额；充值金额必须大于 0，消费金额和余额不得小于 0 |
| 时间 | 使用 UTC 文本 `YYYY-MM-DD HH:MM:SS`，不带 `T`、`Z` 或时区偏移；前端展示时自行转换时区 |
| 手机号 | 使用字符串，保留前导零和国际区号；去空格后非空，最长 20 个字符，不限制为纯数字 |
| 可空文本 | 响应使用 `null`，不使用缺失字段代替空值 |
| 充值平台 | 仅允许 `微信`、`支付宝`、`现金` |
| 消费时长 | `durationMinutes` 为大于或等于 0 的整数分钟 |

新增和修改时，服务端对文本去除首尾空格。新增客户的可选文本省略或传 `null` 时保存为 `null`；修改客户时，字段省略表示保持不变，传 `null` 或空字符串表示清空可选字段。

### 2.4 分页

分页查询参数：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `page` | 否 | 默认 `1`，大于或等于 1 的整数 |
| `pageSize` | 否 | 默认 `20`，范围为 1～100 的整数 |

分页响应：

```ts
interface PageResult<T> {
  items: T[];
  total: number;
}
```

`total` 为过滤后的总记录数，不是当前页数量。非法分页参数返回 `INVALID_INPUT`。

## 3. 公共响应类型

```ts
interface CraftCategory {
  categoryId: number;
  categoryName: string;
  createTime: string;
}

interface CustomerAccount {
  balanceCents: number;
  customerId: number;
  customerName: string;
}

interface Customer {
  createTime: string;
  customerId: number;
  customerName: string;
  customerPhone: string;
  remark: null | string;
  updateTime: string;
  wechatId: null | string;
  wechatName: null | string;
}

interface CustomerDetailResult {
  account: CustomerAccount;
  customer: Customer;
}

type RechargePlatform = '微信' | '支付宝' | '现金';

interface RechargeRecord {
  amountCents: number;
  customerId: number;
  customerName: string;
  platform: RechargePlatform;
  rechargeId: number;
  rechargeTime: string;
}

interface RechargeTransactionResult {
  account: CustomerAccount;
  rechargeRecord: RechargeRecord;
}

interface ConsumptionRecord {
  categoryId: number;
  categoryName: string;
  consumptionAmountCents: number;
  consumptionId: number;
  customerId: number;
  customerName: string;
  durationMinutes: number;
}

interface ConsumptionTransactionResult {
  account: CustomerAccount;
  consumptionRecord: ConsumptionRecord;
}

interface CategoryConsumptionStatistic {
  categoryId: number;
  categoryName: string;
  consumptionCount: number;
  totalConsumptionAmountCents: number;
  totalDurationMinutes: number;
}
```

关于关联名称字段 `customerName` 与 `categoryName`：

- 凡响应对象携带 `customerId` 的，必须同时返回 `customerName`；携带 `categoryId` 的，必须同时返回 `categoryName`。前端据此直接渲染，不得再请求 `/customers/{customerId}` 或 `/categories` 二次补名。
- 两者都是读取时按外键关联 `customer`、`craft_category` 表补充的展示字段，不在 `customer_account`、`recharge_record`、`consumption_record` 中冗余存储；`apps/backend-mock/db/dal/` 的存储层类型保持不含这两个字段，由接口层关联补齐。
- 两者反映客户、品类的**当前**名称：客户改名后历史充值、消费记录中的 `customerName` 随之变化，品类改名后历史消费记录中的 `categoryName` 随之变化，均不保留历史快照。
- 两者均为服务端生成字段，新增充值、新增消费的请求体不得提交 `customerName` 或 `categoryName`。
- 同一数据在不同接口中的名称必须一致：`CustomerDetailResult` 的 `customer.customerName` 与 `account.customerName` 一致；消费记录的 `categoryName` 与 `CraftCategory.categoryName`、`CategoryConsumptionStatistic.categoryName` 一致。
- `CraftCategory`、`CategoryConsumptionStatistic` 自身已含 `categoryName`，不属于需要关联补齐的场景。

## 4. 接口契约

### 4.1 手工品类

| 方法 | 路径 | 请求 | 成功响应 `data` |
| --- | --- | --- | --- |
| GET | `/categories` | 分页参数；可选 `categoryName`，按品类名模糊查询 | `PageResult<CraftCategory>` |
| POST | `/categories` | `{ categoryName: string }` | `CraftCategory` |
| PUT | `/categories/{categoryId}` | `{ categoryName: string }` | `CraftCategory` |
| DELETE | `/categories/{categoryId}` | 无请求体 | `null` |

约束：

- `categoryName` 去空格后非空，最长 50 个字符。
- 品类名唯一；重复时返回 `DUPLICATE_CATEGORY_NAME`。
- 列表按 `categoryId` 升序排列。
- 品类不存在时返回 `CATEGORY_NOT_FOUND`；已有消费记录时返回 `CATEGORY_HAS_CONSUMPTIONS`，不得物理删除。

### 4.2 客户

| 方法 | 路径 | 请求 | 成功响应 `data` |
| --- | --- | --- | --- |
| GET | `/customers` | 分页参数；可选 `customerName`、`customerPhone`，分别模糊查询 | `PageResult<Customer>` |
| POST | `/customers` | 新增客户字段，见下表 | `CustomerDetailResult` |
| GET | `/customers/{customerId}` | 无请求体 | `CustomerDetailResult` |
| PUT | `/customers/{customerId}` | 修改客户字段，见下表 | `Customer` |
| DELETE | `/customers/{customerId}` | 无请求体 | `null` |

新增与修改字段：

| 字段 | 新增 | 修改 | 规则 |
| --- | --- | --- | --- |
| `customerName` | 必填 | 可选 | 去空格后非空，最长 50 个字符 |
| `customerPhone` | 必填 | 可选 | 字符串，去空格后非空，最长 20 个字符 |
| `wechatId` | 可选 | 可选 | 最长 64 个字符；非空时唯一，可传 `null` 清空 |
| `wechatName` | 可选 | 可选 | 最长 100 个字符，可传 `null` 清空 |
| `remark` | 可选 | 可选 | 最长 500 个字符，可传 `null` 清空 |

约束：

- 修改请求至少包含一个上述字段，否则返回 `INVALID_INPUT`。
- 手机号或微信 ID 重复分别返回 `DUPLICATE_CUSTOMER_PHONE`、`DUPLICATE_WECHAT_ID`。
- 客户列表按 `customerId` 升序排列。
- 新增客户必须在同一事务中创建零余额账户，响应同时返回 `customer` 和 `account`。
- 客户不存在时返回 `CUSTOMER_NOT_FOUND`；详情中账户不存在时返回 `CUSTOMER_ACCOUNT_NOT_FOUND`。
- 已有账户、充值记录或消费记录的客户返回 `CUSTOMER_HAS_RELATED_DATA`，不得物理删除。

### 4.3 客户账户

| 方法 | 路径 | 成功响应 `data` |
| --- | --- | --- |
| GET | `/customers/{customerId}/account` | `CustomerAccount` |

只提供余额查询，不提供直接修改余额的接口。响应同时返回 `customerId`、`customerName` 和 `balanceCents`，前端展示账户信息无需再请求客户详情。客户不存在返回 `CUSTOMER_NOT_FOUND`，账户不存在返回 `CUSTOMER_ACCOUNT_NOT_FOUND`。

### 4.4 充值记录

| 方法 | 路径 | 请求 | 成功响应 `data` |
| --- | --- | --- | --- |
| GET | `/customers/{customerId}/recharges` | 分页参数 | `PageResult<RechargeRecord>` |
| POST | `/recharges` | 新增充值字段，见下表 | `RechargeTransactionResult` |

新增充值字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `customerId` | 是 | 大于 0 的安全整数，客户必须存在 |
| `amountCents` | 是 | 大于 0 的安全整数，单位为分 |
| `platform` | 是 | `微信`、`支付宝`或`现金` |

约束：

- `rechargeTime` 由服务端以 UTC 文本生成，客户端不得传入。
- 历史记录按 `rechargeTime` 降序、`rechargeId` 降序排列。
- 客户不存在返回 `CUSTOMER_NOT_FOUND`；账户不存在返回 `CUSTOMER_ACCOUNT_NOT_FOUND`。
- 成功后响应同时包含新充值流水和最新账户余额，前端不得自行累加余额作为最终结果。
- 列表与新增响应中的 `rechargeRecord`、`account` 均自带 `customerName`，前端不得为补客户名再调用客户详情接口。
- 不提供修改或删除充值流水的接口。

### 4.5 消费记录与统计

| 方法 | 路径 | 请求 | 成功响应 `data` |
| --- | --- | --- | --- |
| GET | `/customers/{customerId}/consumptions` | 分页参数 | `PageResult<ConsumptionRecord>` |
| POST | `/consumptions` | 新增消费字段，见下表 | `ConsumptionTransactionResult` |
| GET | `/consumptions/statistics/by-category` | 无参数 | `CategoryConsumptionStatistic[]` |

新增消费字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `customerId` | 是 | 大于 0 的安全整数，客户必须存在 |
| `categoryId` | 是 | 大于 0 的安全整数，品类必须存在 |
| `durationMinutes` | 是 | 大于或等于 0 的安全整数 |
| `consumptionAmountCents` | 是 | 大于或等于 0 的安全整数，单位为分 |

约束：

- 历史记录按 `consumptionId` 降序排列；列表逐条补齐 `customerName` 和 `categoryName`。
- 客户或品类不存在分别返回 `CUSTOMER_NOT_FOUND`、`CATEGORY_NOT_FOUND`。
- 余额不足返回 `INSUFFICIENT_BALANCE`，不得写入消费流水或扣减余额。
- 成功后响应同时包含新消费流水和最新账户余额；`consumptionRecord` 自带 `customerName`、`categoryName`，`account` 自带 `customerName`，前端不得为补名称再调用客户详情或品类列表接口。
- 不提供修改或删除消费流水的接口。
- 品类统计包含所有品类；无消费记录的品类统计值为 0。按 `totalConsumptionAmountCents` 降序、`categoryId` 升序排列。
- 当前消费表没有消费时间字段，因此阶段五不提供按时间筛选的消费统计，也不得在接口中虚构该字段。

## 5. 错误码约定

| 错误码 | 触发场景 | 前端处理建议 |
| --- | --- | --- |
| `INVALID_INPUT` | 路径、查询或请求体参数格式、长度、整数范围、充值平台等不合法 | 展示 `message` 并保留当前表单内容 |
| `CUSTOMER_NOT_FOUND` | 客户详情、账户、流水或资金操作引用的客户不存在 | 刷新客户列表 |
| `CATEGORY_NOT_FOUND` | 修改、删除或消费引用的品类不存在 | 刷新品类列表 |
| `CUSTOMER_ACCOUNT_NOT_FOUND` | 客户存在但账户缺失 | 提示数据异常并停止资金操作 |
| `DUPLICATE_CATEGORY_NAME` | 品类名重复 | 定位到品类名表单项 |
| `DUPLICATE_CUSTOMER_PHONE` | 客户手机号重复 | 定位到手机号表单项 |
| `DUPLICATE_WECHAT_ID` | 微信 ID 重复 | 定位到微信 ID 表单项 |
| `CUSTOMER_HAS_RELATED_DATA` | 客户存在账户或业务流水，删除被拦截 | 提示保留历史数据，不重复请求 |
| `CATEGORY_HAS_CONSUMPTIONS` | 品类已有消费记录，删除被拦截 | 提示保留历史数据，不重复请求 |
| `INSUFFICIENT_BALANCE` | 消费金额超过当前余额 | 展示余额提示并刷新账户 |
| `BALANCE_OVERFLOW` | 充值后余额超出安全整数范围 | 提示调整充值金额 |
| `BALANCE_CHANGED` | 条件更新发现余额已变化 | 刷新余额后允许用户重试 |
| `INVALID_REFERENCE` | 外键兜底发现客户或品类引用失效 | 刷新基础数据后重试 |
| `INTERNAL_ERROR` | 未预期数据库或服务端异常 | 展示通用错误，不暴露内部细节 |

## 6. 事务与实现约束

1. 新增充值必须调用 `createRecharge`，新增消费必须调用 `createConsumption`，接口层不得直接调用流水写入方法后单独修改余额。
2. 两个资金入口均使用 `IMMEDIATE` 事务；只有事务提交成功后才返回成功响应，任一步骤失败必须整体回滚。
3. 客户和品类预校验用于友好提示，数据库外键始终保留并作为最终一致性保障。
4. 账户余额只由充值、消费事务改变，不开放账户新增、修改或删除接口。
5. `customerName`、`categoryName` 不进入数据库表，由接口层按 `customerId`、`categoryId` 关联 `customer`、`craft_category` 表补齐：账户查询、充值列表、充值结果、消费列表、消费结果必须逐条补齐 `customerName`，消费列表与消费结果必须逐条补齐 `categoryName`，禁止返回缺失这些字段的对象。
6. 阶段五前端 API 类型直接复用本文档字段名，不新增以元为单位的金额字段，也不在请求中提交服务端生成的 ID、余额、时间、`customerName` 或 `categoryName`。消费列表与消费新增统一返回 `ConsumptionRecord`，不再单独定义列表专用类型。
7. 阶段五需要调整通用错误提示逻辑，优先读取 `error.message`，避免将 `error` 对象直接转换为字符串。
