# 拼豆手工店后台管理系统整体实施计划

## 1. 文档定位

本文件是拼豆手工店后台管理系统的整体实施计划，用于说明后续开发顺序、阶段目标、交付物、验收标准和风险事项。

数据表的字段名、类型、长度、约束和表间关系，以数据表设计文档为准：

- [拼豆手工店后台管理系统-数据表设计.md](./拼豆手工店后台管理系统-数据表设计.md)

字段或表结构发生变化时，必须先更新数据表设计文档，再同步修改本计划及相关代码。

## 2. 当前项目基础

| 项目 | 现状 |
| --- | --- |
| 前端框架 | Vben Admin，主要位于 `apps/web-ele` |
| Mock 服务 | `apps/backend-mock`，基于 Nitro |
| 业务代码 | 暂无客户、手工品类、充值、消费等业务模块 |
| 数据库 | SQLite |
| 设计基线 | 已完成五张表的数据表设计 |

当前仓库更偏前端工程，后端业务能力尚未建立，因此实施顺序应先固定数据库落地方案和接口契约，再进行页面开发。

## 3. 业务模块范围

## 5. 阶段计划

### 阶段一：数据库方案与跨设备协作约定确认

**目标**：只确定 SQLite 技术方案和多设备协作规则，不在本阶段创建业务迁移脚本或初始化数据库。

**阶段状态**：已完成（方案与约定确认完成，不含数据库初始化落地）

**后续设备执行提示**：阶段一无需重复执行；请先进入阶段二完成数据库初始化与迁移机制。

**主要工作**

1. 【已确认】SQLite 数据库文件存放位置：`apps/backend-mock/data/store.db`。
2. 【已确认】迁移方式：采用 `better-sqlite3` + 版本化 SQL 迁移脚本；后续表结构复杂度明显增加时再评估是否引入 Drizzle。
3. 【已确认】表类型：SQLite 使用严格表。
4. 【已确认】字段映射规则：数据库字段使用蛇形命名，TypeScript 字段使用小驼峰命名，例如 `customer_phone` 对应 `customerPhone`。
5. 【已确认】外键策略：引用完整性由数据库外键约束强制保证；每个 SQLite 连接必须显式启用外键，业务代码负责预校验、删除保护和友好错误处理。
6. 【已确认】Git 提交边界：本地数据库文件不提交，迁移脚本、种子脚本和 `.env.example` 提交。

**已确认决策**

| 决策项 | 决策结果 |
| --- | --- |
| 数据库文件位置 | `apps/backend-mock/data/store.db` |
| 迁移方式 | `better-sqlite3` + 版本化 SQL 迁移脚本 |

   - `.env.local` 已被 `.gitignore` 忽略。

6. **迁移文件协作规则**
   - 迁移文件只能新增，不修改已合并到主分支的迁移文件。
   - 使用版本号或时间戳命名。
   - 迁移版本记录表和迁移执行命令在阶段二实现。

### 阶段二：数据库初始化与迁移机制落地

**目标**：把阶段一的决策和数据表设计文档转换为可运行、可重复执行的数据库初始化能力。

**阶段状态**：已完成（连接配置、迁移命令、种子脚本与本机验证全部落地）

**主要工作**

1. 【已完成】安装并配置 `better-sqlite3`，确认其内置 SQLite 版本为 3.37 及以上。实际安装 `better-sqlite3@13.0.3`，该版本通过 N-API 预编译二进制发布（含 `win32-x64`），无需 Python 和 C++ 构建工具；内置 SQLite 版本为 `3.53.4`，满足严格表要求。已在 `pnpm-workspace.yaml` 中登记 catalog 依赖与 `allowBuilds`（否则安装脚本被忽略、原生模块无法加载），并新增连接配置 `apps/backend-mock/utils/db.ts`：解析 `DATABASE_PATH`、创建数据目录、启动时校验 SQLite 版本、显式启用 `foreign_keys`、`busy_timeout` 与 WAL。
2. 【已完成】创建 `db/migrations` 和 `db/seed` 目录，并添加 `.gitkeep` 占位文件，确保目录可被 Git 跟踪。
3. 【已完成】已新增 `schema_migrations` 迁移文件 `apps/backend-mock/db/migrations/0001_create_schema_migrations.sql`，并已通过 `pnpm db:migrate` 实际执行，`schema_migrations` 表已建立并记录 6 条迁移版本。
4. 【已完成】编写五张业务表的 SQL 迁移文件，使用严格表并定义外键关系；文件为 `0002` 至 `0006`。
5. 【已完成】创建主键、唯一索引和普通索引；主键和唯一约束随建表创建，普通索引分别写入 `0003`、`0005`、`0006` 迁移文件。
6. 【已完成】添加检查约束，例如金额、时长、充值平台取值。金额约束为 `balance_cents >= 0`、`amount_cents > 0`、`consumption_amount_cents >= 0`；时长约束为 `duration_minutes >= 0`；平台约束为 `platform IN ('微信', '支付宝', '现金')`。同时补充文本去空格非空检查，以及 `create_time`、`update_time`、`recharge_time`、`executed_at` 的 `YYYY-MM-DD HH:MM:SS` 时间格式检查；已用 SQLite 3.53.4 逐个用例验证非法数据被拒绝。
7. 【已完成】在每个数据库连接中显式启用外键；客户和手工品类删除采用 `RESTRICT` 或 `NO ACTION`，不级联删除充值、消费流水。连接创建入口统一为 `apps/backend-mock/utils/db.ts` 的 `createDatabase`，内部执行 `PRAGMA foreign_keys = ON`；迁移中 `customer_account`、`recharge_record`、`consumption_record` 的外键均为 `ON DELETE RESTRICT`。
8. 【已完成】实现迁移执行命令 `pnpm db:migrate`。脚本为 `apps/backend-mock/db/migrate.ts`，按文件名升序执行未记录的迁移文件，每个文件与其版本记录在同一事务中提交，失败整体回滚；缺少对应迁移文件的已记录版本会给出警告；同时提供根目录 `pnpm db:migrate` 与包内 `pnpm -F @vben/backend-mock db:migrate` 两种入口。
9. 【已完成】编写初始化种子脚本。执行命令 `pnpm db:seed`，脚本为 `apps/backend-mock/db/seed.ts`，执行 `db/seed/init_craft_categories.sql` 写入默认手工品类（拼豆、奶油胶、马赛克、黏土、布艺），使用 `INSERT OR IGNORE` 保证可重复执行；迁移未执行时会给出明确提示。
10. 【已完成】验证新设备可以从空数据目录生成一致的数据库结构。已删除本地数据库文件后执行 `pnpm db:migrate` 生成 6 张表，重复执行迁移不重复建表、不重复写入版本；`pnpm db:seed` 连续执行两次品类数量保持不变。

- 从空数据目录执行迁移后，可创建五张业务表和 `schema_migrations` 表。
- 重复执行迁移不会重复建表或重复写入迁移版本。
- 所有业务表均使用严格表，外键关系正确且已在每个连接中实际启用。

### 阶段三：数据访问层与事务规则

**目标**：保证余额变动和流水记录一致。

**阶段状态**：已完成（五表数据访问、资金事务、删除保护与本机验证全部落地）

**主要工作**

1. 【已完成】按表建立数据访问方法，代码位于 `apps/backend-mock/db/dal/`，所有方法显式接收同一个 `better-sqlite3` 连接，并将蛇形数据库字段映射为小驼峰 TypeScript 字段。
2. 【已完成】金额统一使用“分”处理，充值金额要求为大于 0 的安全整数，消费金额要求为大于或等于 0 的安全整数，禁止使用浮点数。
3. 【已完成】时间统一使用 UTC 文本格式，由 `getUtcTimestamp` 生成 `YYYY-MM-DD HH:MM:SS`；客户修改时同步刷新 `update_time`。
4. 【已完成】充值记录写入与余额增加使用同一事务，业务入口为 `apps/backend-mock/db/transactions.ts` 的 `createRecharge`。
5. 【已完成】消费记录写入与余额扣减使用同一事务，业务入口为同文件的 `createConsumption`。
6. 【已完成】删除客户或手工品类前检查是否存在关联数据；已有账户或业务流水的客户、已有消费记录的品类均拒绝物理删除，数据库外键继续作为最终保障。
7. 【已完成】新增充值、消费前由业务代码预校验客户和手工品类是否存在，并将数据库外键错误转换为 `BusinessError`；代码校验不替代数据库约束。

**数据访问层设计**

| 文件 | 主要能力 |
| --- | --- |
| `dal/craft-category.ts` | 品类查询、新增、修改、删除保护 |
| `dal/customer.ts` | 客户查询、资料维护、删除保护；建档与零余额账户初始化同事务完成 |
| `dal/customer-account.ts` | 按客户查询账户及账户列表 |
| `dal/recharge-record.ts` | 充值流水查询及仅供事务调用的写入方法 |
| `dal/consumption-record.ts` | 按客户或品类查询消费流水及仅供事务调用的写入方法 |
| `dal/shared.ts` | UTC 时间、整数分与文本校验、业务错误和 SQLite 错误识别 |
| `db/transactions.ts` | 充值与消费跨表事务，返回最新流水和账户余额 |

**事务处理规则**

1. 充值、消费及客户建档使用 `IMMEDIATE` 事务，在预校验前取得写锁，避免并发写入导致余额判断失效。
2. 事务内再次确认客户、账户及消费品类存在；流水只能由对应资金事务写入，不提供独立的业务新增入口。
3. 充值先写流水再按原余额条件更新账户；消费先校验余额，再写流水并按原余额条件扣减。任一语句失败或条件更新未命中都会抛出错误并整体回滚。
4. 余额增加前检查结果仍为安全整数；余额不足返回 `INSUFFICIENT_BALANCE`，不留下消费流水。
5. 外键约束始终保持启用；业务预校验用于友好提示，捕获到的外键错误也会转换为明确的业务错误。

**交付物**

- 五表数据访问层及统一字段映射
- 充值、消费和客户建档事务
- 业务预校验、删除保护与外键错误转换
- 数据访问层及事务自动化测试

**验收标准**

- 充值成功后余额正确增加。
- 消费成功后余额正确扣减。
- 任一步骤失败时数据可回滚。
- 余额不足时消费失败。

**验收结论**：已通过 12 个 Node 环境下的内存数据库测试，覆盖充值和消费成功、余额不足、客户或品类不存在、余额更新失败回滚流水、账户初始化失败回滚客户、删除保护、整数分及 UTC 时间规则；TypeScript 类型检查通过。

## 6. 关键规则基线

以下内容必须始终与数据表设计文档保持一致：

1. 金额统一以“分”为单位的整数存储，不使用浮点数。
2. 时间统一保存为 UTC 文本，展示时再转换时区。
3. 充值平台仅允许微信、支付宝、现金。
4. 外键引用完整性由数据库约束强制保证，每个 SQLite 连接必须显式启用外键；业务代码只负责预校验、删除保护和友好错误处理，不能替代数据库约束。
5. 已产生业务记录的客户和手工品类不宜直接物理删除。
6. 充值和消费记录属于业务流水，不建议随意修改或删除。
7. 数据库字段名以数据表设计文档为准，例如客户手机字段为 `customer_phone`。
8. 开台与续时只写会话并累计应付金额与时长，不写消费流水、不扣减余额；消费流水只在结账时生成。开台支持两种计时方式：按购买时长倒计时（支持续时）与实际计时（不设结束时间、从开台起正计时、不支持续时，结账按实际用时向上取整到分钟结算）。购买时长模式结账实收金额不得超过应付金额，实际计时模式实收金额由门店按实际用时确定；余额不足拒绝结账且座位保持占用；关台（免结账）直接结束会话释放座位，不产生流水与资金变动。桌位看板当日「累计已结」只统计结账流水实收金额。
